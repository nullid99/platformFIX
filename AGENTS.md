# Инструкции проекта

Этот файл является обязательным рабочим правилом для любых изменений в проекте.

## Перед началом работы

1. Сначала прочитать этот файл и документы из `docs/`.
2. Проверить структуру проекта, существующие соглашения и `git status`.
3. Не удалять и не перезаписывать изменения, сделанные пользователем.
4. Разобрать запрос по чек-листу из `docs/request-checklist.md`.
5. Если запрос затрагивает безопасность, деньги, права доступа или данные пользователей и требование неоднозначно, явно зафиксировать допущение либо задать вопрос до реализации.

## Технологический стек

- TypeScript в strict mode.
- Next.js App Router для web-приложения.
- NestJS для API.
- PostgreSQL как основная база данных.
- Prisma для схемы и миграций.
- Redis и BullMQ для очередей, блокировок и фоновых задач.
- S3-compatible storage для файлов.
- Docker Compose для локального запуска и деплоя на Hetzner.
- Vitest для unit/integration-тестов.
- Playwright для E2E-тестов.

## Правила реализации

- Сначала использовать существующие паттерны проекта, затем добавлять новые абстракции.
- Бизнес-логика находится в use case/service, а не в UI-компонентах или HTTP-контроллерах.
- Web не обращается к PostgreSQL напрямую.
- Доступ проверяется на сервере для каждой защищённой операции и каждого защищённого медиа-ресурса.
- Все изменения базы данных выполняются через миграции.
- Webhook-и, загрузки и фоновые задачи должны быть идемпотентными.
- Секреты, токены и персональные данные не попадают в логи и репозиторий.
- Не использовать `any` без локального комментария с обоснованием.
- Не добавлять зависимости без необходимости и проверки лицензии/поддержки.
- Не смешивать в одной задаче функциональные изменения и несвязанный рефакторинг.

## После реализации

1. Запустить подходящие lint, typecheck и тесты.
2. Проверить изменённые пользовательские сценарии вручную или через E2E.
3. Проверить отрицательные сценарии: чужой объект, просроченный доступ, повторный запрос, пустые и слишком большие данные.
4. Просмотреть diff и убедиться, что нет секретов, отладочного кода и лишних изменений.
5. В финальном отчёте указать изменённые файлы, проверки и оставшиеся риски.
